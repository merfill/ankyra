# План реализации — Ankyra

> Русская версия для чтения. Каноничный документ — `docs/implementation_plan.md`.

Статус: **черновик**. Архитектура согласована в обсуждении; открытые решения
помечены `OPEN`. Этот документ фиксирует согласованную архитектуру и все
альтернативы, которые нельзя забыть. Техническое задание (`docs/task.md`) будет
приведено в соответствие этому плану после закрытия открытых решений ниже.

## 1. Цель

Домен-независимый гибридный нейро-символический движок рассуждений. LLM
предлагает; детерминированный символический движок классифицирует, выводит и
верифицирует. LLM не владеет истиной: предлагать она может свободно, но каждое
предложение либо лицензировано теорией, либо заземлено цитатой, либо записано как
явная гипотеза.

## 2. Согласованная архитектура

### Фаза 0 — декомпозиция (специальная обработка текста)

Отдельная стадия, выдающая три самостоятельных артефакта и никогда их не смешивающая:

- `theory_structure` — факты и правила, извлечённые из описательной части;
- `question_structure` — цель `phi` (с переменными для «какой/кто/что»), константы
  вопроса и условия `Gamma`, которые вопрос утверждает;
- `answer_type ∈ {yes_no, open, instruction}` (для `instruction` ⇒ `phi = null`).

Жёсткое правило: вопрос никогда не утверждается как факт (эквивалент
`_drop_goal_echo` в OntoLegal). Вопрос выражается словарём теории, когда это
возможно; если выразить нельзя — сохраняется дословно, чтобы верификация честно
сообщила `target_unmatched`.

### Фаза 1 — детерминированное ядро (спина)

- Модель данных: `Object`, `Morphism` (`predicate, subject, object, quote, negated`),
  `Rule` (`conditions` AND → `consequence`), `Theory` (`objects`, `morphisms`
  = аксиомы, `rules`), `Query` (`conditions`, `target`, `variables`).
- `saturate`: прямой вывод до неподвижной точки (полу-наивно), завершается на
  конечном универсуме; каждый выведенный факт несёт историю вывода (`used`, `witness`,
  `rule_index`).
- `unify` / `match_goal`, `complementary` (P ∧ ¬P), транзитивное замыкание
  положительного `is_a`.
- `verify(Theory ∪ Gamma ⊢ phi)` → вердикт со статусом
  `supported | insufficient | unsupported | refuted` и структурированными gap'ами
  (`target_unmatched:`, `condition_unmatched:`, `unused_premise:`, `contradiction:`).
- Этот слой звуков и полон **относительно формализации**. Ему запрещено добавлять
  знание.

### Фаза 2 — направляемый цикл

Внутренняя петля (детерминированная, без LLM): `saturate` до неподвижной точки.
Внешняя волна (LLM), повторяется:

1. `verify(state)` → вердикт + структурированные gaps.
2. Сборка подсказки: структура задачи + словарь теории + достигнутый фронт + gaps +
   цель + правила заземления.
3. Свободное рассуждение LLM → одно типизированное предложение + нарратив.
4. Детерминированная классификация предложения:
   | категория | условие | действие движка |
   |---|---|---|
   | `derivable` | уже выводится | принять только как нарратив |
   | `cited` | новый факт с валидной дословной цитатой | добавить в аксиомы |
   | `hypothesis` | новое правило/факт вне текста | леджер гипотез, метка `H` |
   | `rejected` | схема / safety / цитата не проходят | отбросить с кодом причины |
5. Применить принятые добавления, снова прогнать внутреннюю петлю, перепроверить.
6. Стоп при `supported` / `refuted` / `no_progress` / бюджет / нет достижимой гипотезы.

Рампа свободы (политика, не архитектура): волна 0 разрешающая (свободное
именование предикатов, гипотезы разрешены и помечены); последующие волны
ограничивают — канонизируют имена, требуют переиспользования словаря, при желании
запрещают гипотезы (`ANKYRA_ALLOW_HYPOTHESES=false`).

### Фаза 3 — объяснение

Трассировка строится **механически** из истории вывода (`used`/`witness`). LLM может
только перефразировать готовое дерево вывода; вводить факты она не может. Сила
ответа явная: `proven`, `proven_under(H)` или `not_proven`.

## 3. Инварианты (зафиксированы сейчас, меняются политикой позже)

- **D2.** Ни один факт от LLM не входит в теорию без либо валидной цитаты
  (`cited`), либо явной метки гипотезы (`hypothesis`). Старый ReAct-механизм
  `new_predicates` отвергается полностью.
- **D3.** Монотонность: база только растёт; цель никогда не ослабляется; удаления
  посылок нет. (Оставляем сейчас; позже можно ослабить политикой.)
- **D4.** Сила ответа сообщается всегда (`proven` vs `proven_under(H)`).
- **D5.** Фаза 0 разделяет теорию и вопрос.
- **D6.** Свобода в предложении, детерминизм в классификации.
- **G1.** Одно действие предложения на волну; каждая волна оставляет проверяемый след.
- **Зафиксировано (решение):** леджер гипотез, сила ответа, классификация
  предложений и `Rule.source` — **ядро**, не опция. Режим гипотез по умолчанию —
  разрешающий-с-метками (`ANKYRA_ALLOW_HYPOTHESES=true`); строго-только-цитата —
  переключатель. В силу ответа идут только гипотезы, вошедшие в доказательство.
- **Зафиксировано (решение):** модальность — первоклассное поле
  `Morphism.modality`; имена предикатов по умолчанию без префикса; понижение в
  стиле OntoLegal — за `ANKYRA_DEONTIC_PREFIXES`.
- **Зафиксировано (решение):** оркестрация — LangGraph (`StateGraph`), линейный граф
  с ограниченным циклом рассуждения.

## 4. Примеры как приёмочные тесты

### Пример A — дождь (чистая дедукция, 1 волна, без гипотез)

- Фаза 0: теория = `{raining()}` + правило `R1: raining() => isWet(ground)`;
  вопрос `phi = isWet(ground)`, тип `yes_no`, `Gamma = {}`.
- Волна 0 (только детерминированно): `saturate` срабатывает по `R1`; `verify` →
  `supported`.
- Ожидание: ответ «да», объяснение из истории вывода. LLM в цикле не вызывается.

### Пример B — транспорт (абдукция, N волн, гипотезы)

- Фаза 0: теория = факты `hasEngine(X)`, `wheelCount(X,4)`, `power(X,150)`,
  `doorCount(X,4)`; **правил нет** (правила классов в тексте отсутствуют);
  вопрос `phi = is_a(X, ?c)`, тип `open`.
- Волна 0: замыкание ничего не даёт для `phi`; `verify` → gap `target_unmatched: is_a`.
- LLM предлагает правила классов + иерархию. Цитат из текста у них нет ⇒ категория
  `hypothesis` (`H1`, `H2`, `H3`, `Hh` для `is_a(car, motorVehicle)`,
  `is_a(sedan, car)`).
- Повторное замыкание: `is_a(X, motorVehicle)`, `is_a(X, car)`, `is_a(X, sedan)` +
  транзитивное `is_a`. `match_goal(is_a(X, ?c))` связывает `?c`; «самый специфичный»
  теперь **определён** цепочкой `is_a`, а не угадан.
- Ожидание: «X — седан, **при** H1, H2, H3, Hh». С запретом гипотез — честный
  отказ. Этот пример заодно показывает ключевой факт: правила классов никогда не
  были в исходном тексте.

## 5. РЕШЕНО — сравнения / builtins (решение D1)

Статус: **РЕШЕНО** — v0 выходит без builtins; v0.1 добавляет вычислитель.
Кусается на примере B (`power > 50`, `wheelCount >= 4`).

### Вариант A — минимальный range-restricted builtin-вычислитель

- Закрытый набор: `=`, `neq`, `<`, `lte`, `>`, `gte` над числовыми литералами.
- Safety: каждая переменная в builtin-цели должна быть связана более ранним
  положительным реляционным атомом в том же теле правила; иначе правило отвергается.
- Семантика: builtin-атом не сопоставляется с фактами — он *вычисляется*,
  фильтруя подстановки во время унификации.
- Плюсы: пороги/свойства выражаются напрямую; не засоряем леджер гипотез тривиальной
  арифметикой; детерминирован и по-прежнему звуков (builtin вычислим, а не выучен);
  закрывает пример B без гипотез для числовой части.
- Минусы: нужен домен значений (числовые литералы), парсинг чисел, извлечённых из
  текста, и строгое соблюдение range-restriction для завершаемости.

### Вариант B — без builtins; пороги как явные предикаты/гипотезы

- LLM предлагает, например, `powerAbove50(X)` как факт-гипотезу или
  дискретизированный предикат. Всё остаётся Хорновым фактом; домена значений нет.
- Плюсы: движок остаётся тривиальным; никакой новой механики.
- Минусы: леджер заполняется тривиальными числовыми фактами; отображение
  «число → дискретный класс» становится свежей гипотезой каждый раз (плохое
  переиспользование); именно в дискретизации и прячутся ошибки.

### Решение

- **v0:** движок выходит **без** builtins; пример B выражает пороги как
  `hypothesis`. `unify`/`saturate` проектируются с единственной точкой расширения
  (хук `evaluate(builtin_atom, subst)`), чтобы вариант A подключился без переделок.
- **v0.1:** добавить вариант A как первое расширение, в рамках спецификации
  «закрытый набор + safety», за флагом.
- Вариант B держать как задокументированный fallback.

## 6. Прочие открытые вопросы

- **Режим гипотез (РЕШЕНО).** По умолчанию разрешающий-с-метками
  (`ANKYRA_ALLOW_HYPOTHESES=true`); строго-только-цитата — за переключателем.
- **Оркестрация (РЕШЕНО).** LangGraph `StateGraph`, линейный граф с ограниченным
  циклом (раздел 9 в `docs/task_ru.md`). `langgraph` остаётся зависимостью.
- **Поиск (РЕШЕНО — неприменимо).** Ankyra не поисковая система и фрагментов у неё
  нет. Вход — одна самодостаточная задача; движок рассуждает прямо по ней. Слоя
  recall/rerank/выравнивания к фрагменту нет.
- **Деонтическая модальность (РЕШЕНО).** Модальность — первоклассное поле
  `Morphism.modality`; имена предикатов по умолчанию без префикса. Понижение до
  `must_`/`must_not_`/`may_` в стиле OntoLegal живёт за `ANKYRA_DEONTIC_PREFIXES`
  (с polarity fold и фиксом двойного префикса). Вариант A (всегда префикс)
  остаётся задокументированным fallback.

## 7. Вехи (предварительно)

1. Модель данных + схемы извлечения Фазы 0.
2. Детерминированное ядро (saturate / unify / verify / история вывода) + тесты на примере A.
3. Направляемый цикл с леджером гипотез + тесты на примере B.
4. Механическое объяснение из истории вывода; опциональный пересказ LLM.
5. Точка расширения для builtins (вариант A) за флагом.

## 8. Беклог (из eval-харнесса)

Источник: `docs/quality_findings_ru.md`. По приоритету.

1. **Верность объяснения (баг).** `build_explanation` должен учитывать терминальный
   статус: `target_refuted` → отрицательный вывод; `contradiction` / unsupported →
   пустой трейс. Сейчас при `refuted` показывается позитивный вывод: `exception`
   выводит и `fly(tweety)`, и `NOT fly(tweety)` (свидетели `rule:1`/`rule:2`), но в
   трейсе только позитивная ветка. Выявлено при просмотре русской наррации;
   **сначала решить, как именно показывать, потом кодить.**
2. **Провенанс правил в объяснении.** Перестать `enrich.materialize_rule_morphisms`
   превращать следствие правила в аксиому (или сохранять историю вывода при материализации),
   чтобы правило попадало в трейс: `rain` показывает `wet(ground)` как аксиому и
   прячет правило. Выявлено при просмотре наррации; **сначала решить.**
3. **Захват презумпций.** Надёжно заводить клаузы «given that / assuming» в условия
   вопроса (строже промпт вопроса + шире примеры, либо отдельный проход по вопросу).
4. **Митигации вариативности.** Мультисэмпл извлечения `ANKYRA_EXTRACT_SAMPLES` с
   детерминированным выбором; стабильнее промпты; seed провайдера при наличии.
5. **Немонотонные исключения (заметка готова).** См. `docs/defeasible_reasoning_ru.md`:
   предлагаемая семантика = defeasible-правила + negation-as-failure + специфичность по
   `is_a`, под well-founded семантикой, за флагом. Ждём продуктового решения.
6. **Кейс builtins.** Отдельный eval, реально проверяющий пороги `gte`/`gt`.
7. **LLM-судья.** Реализовать `LLMJudgeEvaluator` (корректность + эффективность по
   рубрике на задачу) на существующем интерфейсе `Evaluator`.
8. **`ARCHITECTURE.md`** — написан (слои, потоки, карта модулей).
9. **Подключаемая семантика вывода (будущее).** См. `docs/logic_layer_ru.md`:
   выделить узкий протокол `Inference` только когда появится вторая семантика
   (defeasible); не абстрагировать спекулятивно.
