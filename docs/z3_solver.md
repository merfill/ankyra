## Назначение и место модуля в проекте

### Место SMT-бэкенда в архитектуре уровней

Настоящий документ описывает SMT-бэкенд уровня L2 — один из двух взаимозаменяемых способов решать задачи логики первого порядка с кванторами в Ankyra. Бэкенд опирается на решатель SMT (Z3) и потому является **опциональным**: он подключается как отдельная зависимость и активируется значением конфигурационного параметра, а не присутствует в базовой поставке.

Развитие движка организовано как последовательность стадий разрешимых формализмов: L0 (хорновы формулы), L1 (отрицание), L2 (логика первого порядка с кванторами), L3 (задачи удовлетворения ограничений), L4 (числовые задачи); отдельно рассматривается дефолтная (немонотонная) логика. Для каждой стадии определён собственный бенчмарк, выступающий воротами перехода (см. `docs/reasoning_roadmap.md`). SMT-бэкенд закрывает ровно уровень L2: гейтом этого уровня выступает коллекция FOLIO, описанная в `docs/folio.md` и `docs/folio_gold_fed.md`. Уровни L3 (AR-LSAT, `docs/ar_lsat.md`) и L4 (GSM8K, `docs/gsm8k.md`) обслуживаются отдельными движками, и SMT-бэкенд не расширяет сферу действия нижних уровней (L0 Horn, L1 с отрицанием).

### Соотношение с базовым resolution-бэкендом

Выбор бэкенда уровня L2 управляется переменной окружения `ANKYRA_L2_BACKEND`. Значение по умолчанию — `resolution`, не требующее дополнительных зависимостей; значение `smt` переключает уровень на SMT-бэкенд. Оба бэкенда возвращают один и тот же вердикт, то есть с точки зрения истинности вывода они эквивалентны и различаются не логикой, а формой получаемого результата.

Различие существенно для объяснимости. SMT-бэкенд не строит граф доказательства: в возвращаемом объекте `ProverResult` поле `proof` остаётся равным `None`. Как следствие, под `smt` недоступны команда `explain` и учёт неиспользованных посылок — обе возможности опираются на наличие proof DAG и потому работают только при `resolution`. Иными словами, `smt` следует рассматривать как средство получения вердикта, а `resolution` — как средство получения вердикта вместе с его обоснованием.

## Установка и требования

Проект использует пакетный менеджер **uv** (не `pip`) и требует Python версии не ниже 3.11. Базовая установка зависимостей выполняется командой `uv sync` и не включает решатель Z3; офлайн-тесты в такой конфигурации проходят без него. Дополнительная группа зависимостей `smt` нужна исключительно для SMT-бэкенда уровня L2 и ни для каких других режимов работы не требуется:

```bash
uv sync --extra smt
```

При работе только с резолюционным путём команду с `--extra smt` можно не выполнять.

## Архитектура и принцип работы

### Входные данные и трансляция в SMT-LIB

Самодостаточная естественно-языковая задача (условия и вопрос) непосредственно в SMT-бэкенд не попадает. Сначала языковая модель извлекает условия, вопрос и структурированные поля — идентификаторы предикатов и объектов, модальность, вид отношения, признак предикации и ключи слотов. Затем детерминированная формализация (фаза 0, описанная в `docs/task.md` §0.3) строит объект `ProblemStructure`: предикативное «is/are» (`predication: copula`) превращается в `is_a(subject, complement)`, прочие одноместные предикации (например, «has an engine») остаются унарными, а поле `ProblemStructure.domain` задаёт доменные сорта, к которым принадлежат все индивиды задачи. Правило, которое лишь ограничивает переменную доменным сортом, трактуется как область действия квантора, а не как посылка, и потому отбрасывается. Тем самым свойства не попадают в иерархию типов.

При активном значении `ANKYRA_L2_BACKEND=smt` формализованные условия транслируются в язык SMT-LIB: доменные сорта объекта `ProblemStructure` становятся сортами теории, унарные предикаты и отношения — соответствующими символами сигнатуры, а сами условия — набором утверждений. Вопрос задачи проверяется как следствие этого набора, и вердикт выводится из ответа решателя о выполнимости. Взаимодействие с Z3 осуществляется через его программный интерфейс, который появляется в окружении только после установки дополнительной группы зависимостей `smt`.

Трансляция работает с результатом фазы 0, а не с исходным текстом: детерминированный код не интерпретирует естественный язык. Допустимые операции над сырым текстом ограничены структурными проверками свидетелей — дословным вхождением цитаты, её позицией и длиной, а также покрытием текста. Каждое утверждение теории обязано иметь происхождение: оно либо сопровождается дословной цитатой из текста (статус `cited`), либо явной пометкой гипотезы (статус `hypothesis`); второй вариант допустим только при `ANKYRA_ALLOW_HYPOTHESES=true`. Таким образом, бэкенд получает на вход уже проверенную формализацию и отвечает исключительно за проверку логического следствия, не участвуя ни в извлечении знаний, ни в их нормализации.

### Выходные данные

Результатом работы любого бэкенда уровня L2 является объект `ProverResult` — вердикт по вопросу задачи вместе с логическим статусом ответа. Под `smt` этот объект формируется без графа доказательства: поле `ProverResult.proof` имеет значение `None`. Поэтому под SMT-бэкендом недоступны команда `explain` и учёт неиспользованных посылок; `resolution` возвращает вердикт вместе с пошаговым обоснованием, пригодным для narrate-представления и анализа вклада отдельных посылок. При выборе `smt` сохраняются все свойства уровня L2, кроме тех, что связаны с построением и обработкой доказательства.

## Конфигурация

Параметры читаются библиотекой Dynaconf с префиксом `ANKYRA` из файла `.env`; образец допустимых переменных приведён в `.env.example`. Помимо переменной выбора бэкенда, на поведение движка влияют следующие флаги.

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `ANKYRA_L2_BACKEND` | `resolution` | Выбор бэкенда уровня L2: `resolution` или `smt` |
| `ANKYRA_ALLOW_HYPOTHESES` | `true` | Разрешает приём утверждений со статусом `hypothesis` |
| `ANKYRA_BUILTINS` | `false` | Включает встроенные (предопределённые) элементы теории |
| `ANKYRA_MAX_WAVES` | `8` | Ограничение числа волн рассуждения |
| `ANKYRA_LANG` | `en` | Язык повествования (narration), например `ru` |

Выбор вычислительного ядра производится переменной окружения:

```bash
export ANKYRA_L2_BACKEND=smt
```

## Ограничения и известные особенности

### Отсутствие трассы вывода под SMT-бэкендом

Наиболее существенное ограничение режима `smt` следует из способа его работы: решатель возвращает корректный вердикт, но не возвращает доказательства. Поле `ProverResult.proof` остаётся пустым (`None`), поскольку SMT-бэкенд не строит доказательство в виде направленного ациклического графа. Практическим следствием этого является то, что команда `explain` и учёт неиспользованных посылок (unused-premise accounting) работают только под резолюционным бэкендом. Если требуется не только вердикт, но и пошаговое обоснование либо анализ вклада отдельных посылок, следует переключиться на `ANKYRA_L2_BACKEND=resolution`: оба бэкенда дают одинаковый вердикт, поэтому такая замена не влияет на результат вывода, а лишь восстанавливает доступ к трассировке.

### Зависимость от опционального расширения

Z3 подключается как опциональное расширение `smt` и устанавливается командой `uv sync --extra smt`. Базовая установка (`uv sync`) и офлайн-тесты (`uv run pytest`) этого расширения не требуют, так как по умолчанию выбран бэкенд `resolution`.

### Границы уровня L2

Ответственность модуля ограничена уровнем L2 в терминологии `docs/reasoning_roadmap.md`, то есть логикой первого порядка с кванторами. Остальные стадии лестницы формализмов реализуются вне данного модуля: уровень L3 (задачи удовлетворения ограничений, AR-LSAT, см. `docs/ar_lsat.md`) и уровень L4 (числовые задачи, GSM8K, см. `docs/gsm8k.md`) обслуживаются отдельными движками. SMT-бэкенд не следует рассматривать как универсальный решатель: он закрывает ровно один сегмент роадмапа и не расширяет сферу действия нижних уровней (L0 Horn, L1 с отрицанием).

### Сводная таблица ограничений

| Ограничение | Проявление | Комментарий |
| --- | --- | --- |
| Отсутствие proof DAG | `ProverResult.proof is None`; недоступны `explain` и учёт неиспользованных посылок | Переключение на `ANKYRA_L2_BACKEND=resolution` даёт тот же вердикт вместе с трассировкой |
| Опциональная зависимость Z3 | Требуется `uv sync --extra smt`; нужен Python ≥ 3.11 и пакетный менеджер `uv` | Базовой установке и офлайн-тестам расширение не нужно |
| Уровень L2 | Поддерживаются кванторные выводы логики первого порядка | L3 (CSP, `docs/ar_lsat.md`) и L4 (числа, `docs/gsm8k.md`) — отдельные движки |

## Примеры использования

### Прогон eval-харнесса под SMT

Чтобы направить вывод уровня L2 в SMT-бэкенд, достаточно выставить переменную окружения `ANKYRA_L2_BACKEND` в значение `smt`. Переменная читается через Dynaconf с префиксом `ANKYRA`, поэтому её можно задать как на всю сессию, так и на одну команду:

```bash
export ANKYRA_L2_BACKEND=smt
uv run python -m evals.run --ids rain,vehicle
```

Эквивалентная запись в одну строку:

```bash
ANKYRA_L2_BACKEND=smt uv run python -m evals.run --ids rain,vehicle
```

Параметр `--ids` принимает перечень идентификаторов задач через запятую; приведённые `rain` и `vehicle` — примеры из документации проекта, и при прогоне их следует заменить на фактические идентификаторы из коллекции. По завершении прогона рассуждение читается тем же способом, что и для остального харнесса:

```bash
uv run python -m evals.narrate --lang ru
```

Флаг `--lang ru` задаёт язык повествования; значение по умолчанию определяется настройкой `ANKYRA_LANG` (по умолчанию `en`).

Проверить корректность установки и самого движка можно штатным набором тестов; живые тесты с реальными вызовами LLM выполняются отдельно и по умолчанию пропускаются:

```bash
uv run pytest
ANKYRA_LIVE=1 uv run pytest -m live
```

### Сравнение с resolution-путём

Оба бэкенда — `resolution` (по умолчанию) и `smt` — дают одинаковый вердикт по одной и той же формализованной задаче, поэтому выбор между ними не влияет на правильность ответа, а определяет полноту сопроводительных данных. Под `smt` результат `ProverResult` не содержит proof DAG (`ProverResult.proof is None`), вследствие чего недоступны пояснение (`explain`) и учёт неиспользованных посылок. Чтобы получить вердикт вместе с трассировкой, тот же прогон повторяют без переопределения бэкенда:

```bash
unset ANKYRA_L2_BACKEND
uv run python -m evals.run --ids rain,vehicle
uv run python -m evals.narrate --lang ru
```

Таким образом, типичный порядок работы состоит в том, чтобы использовать `resolution` для разбора и объяснения рассуждений, а `smt` — как независимый способ проверки того же вердикта средствами SMT-решателя; расхождение результатов двух прогонов служит диагностическим признаком ошибки в формализации или в трансляции задачи в SMT-LIB.
