# Маршрутизация фрагментов — контракт объявленного фрагмента

Статус: **утверждённый план** (A1: первый инкремент — только валидация); ещё не
реализован. Решения `D-FR-1`…`D-FR-6` в §9 — **DECIDED**. Это рабочий план выбора
решающей процедуры по структуре, построенной Фазой 0, на уровне стадий
`docs/reasoning_roadmap.md`.

Канонический язык: английский; русское зеркало: `docs/fragment_routing_ru.md`.
Связанное: `docs/reasoning_roadmap.md`, `docs/logic_layer.md` (шов `Inference`),
`docs/l1_plan.md`, `docs/l2_plan.md`, `docs/defeasible_reasoning.md`,
`docs/task.md`.

## 1. Проблема

Как Ankyra выбирает логику для задачи, когда логика заранее неизвестна? Ответ
обязан сохранить принцип проекта (**LLM предлагает, движок решает**) и не
угадывать семантику.

Два соблазнительных ответа отвергается:

- **Пробовать каждую логику.** Неэффективно, и позволяет более выразительному
  формализму перекрыть честный вердикт более слабого, из-за чего заявленный ответ
  зависит от поиска, а не от объявленного прочтения.
- **Спросить LLM, какая логика.** LLM авторизует формализацию, а не семантику
  вопроса; просьба выбрать логику переделегирует решение, которым она не владеет
  (`docs/task.md` §3.8).

Остаётся ответ — детерминированный, аудируемый выбор по **структуре**, которую
Фаза 0 уже построила — но его надо сформулировать точно, потому что «логика»
смешивает три разные вещи.

## 2. Три оси, три источника

| Ось | Примеры | Источник | Момент |
|---|---|---|---|
| **Фрагмент** (выразительность) | `horn`, `negation`, `disjunction`, `existential`, `builtin` | **выводится** из построенных `Theory`/`Query` | статически, до решения |
| **Семантика** | открытый/закрытый мир, монотонная/дефолтная | **объявляется** вопросом/бенчмарком (`Query.world_assumption`; `DEFEASIBLE`) | статически |
| **Процедура** | forward chaining Хорна, clausal resolution | **выводится** из фрагмента ∧ семантики | статически |

Ключевое разделение: **фрагмент — функция структуры, которую произвела LLM;
семантика объявляется извне.** Движок никогда не выводит закрытый мир из
отрицания-по-неудаче или из отсутствия фактов (это уже правило `docs/l1_plan.md`
D-L1-4).

Следствие, сформулированное честно: LLM **действительно** выбирает фрагмент
**формой извлечения** (`StructDisjunction` против факта, `StructRule.consequents`
против `consequent`, `StructExistential`). Движок не отнимает эту власть; он
делает её аудируемой и ограничивает радиус поражения набором возможностей (§4).
Гарантия движка — про **истину** (`proven`/`refuted`), а не про то, какой фрагмент
эмитировало извлечение.

## 3. Вывод фрагмента (чистый)

Требуемый фрагмент вычисляется из построенных структур существующими
структурными предикатами (`engine/horn.py`):

- `horn` — `not has_non_horn(theory)`, нет `Theory.existentials`, и
  `query.goal_mode == "single"`.
- `negation` — непустые `Theory.constraints` (дизъюнктность) или отрицательный
  литерал в теле/голове правила.
- `disjunction` — `has_non_horn(theory)` (дизъюнктивная **голова** или
  дизъюнктивный ground-факт).
- `existential` — непустые `Theory.existentials` или экзистенциальная цель.
- `compound_goal` — `query.goal_mode != "single"` (конъюнктивная или дизъюнктивная
  цель).
- `builtin` — предикат сравнения (`engine/builtins.is_builtin`).

Замечание: дизъюнктивный **антецедент** уже расщепляется builder'ом на одно
Horn-правило на атом (`(A ∨ B) → C ≡ (A → C) ∧ (B → C)`); он фрагмент **не**
повышает. Только дизъюнктивная голова и составная цель требуют clausal-процедуры.

## 4. Набор возможностей (подход A)

Флаги перечисляют процедуры, которые прогон **может** использовать; они не
называют семантику.

| Возможность | Флаг | По умолчанию |
|---|---|---|
| `horn` | доступна всегда | вкл |
| `clausal` (L2) | `ANKYRA_LOGIC` ≠ `off` | выкл |
| `builtin` | `ANKYRA_BUILTINS` | выкл |
| `defeasible` | `ANKYRA_DEFEASIBLE` | выкл |

`world_assumption` — **не** возможность: это объявленная семантика, её несёт
запрос, а по умолчанию задаёт `ANKYRA_NEGATION_MODE` (`build/pipeline.py`).

Набор возможностей — **параметр прогона**:

- **гейты/абляции** пинят или сужают его, чтобы «это число получено
  Horn-процедурой» было утверждением об именованном формализме;
- **продуктовый рантайм** расширяет его, чтобы одиночный пользовательский запрос
  использовал сильнейшую звуковую процедуру, которую допускает объявленная
  семантика, и честно отказывал иначе.

Гейтовый случай — частный случай продуктового (множество из одного элемента).
Поэтому это один механизм, а не два.

## 5. Решение и валидация

Статическое, тотальное решение (без итераций):

```python
class RoutingDecision:
    required_fragment: frozenset[FragmentFeature]
    declared_semantics: dict          # world_assumption, defeasible
    capabilities: frozenset[str]
    procedure: str                    # "horn" | "clausal"
    compatible: bool
    reasons: list[str]                # напр. "disjunction:head_alternatives"
```

- фрагмент ⊆ `{horn, negation, builtin}` → `horn`;
- фрагмент содержит `disjunction` или `existential` → `clausal`;
- объявлена `defeasible` → дефолтный слой поверх выбранной базовой процедуры;
- если выбранная процедура не может удержать **объявленную** семантику, или
  требуемый фрагмент вне набора возможностей → `out_of_fragment`, с именованным
  gap-кодом (никогда — тихий прогон не под той семантикой).

Коды отказа: `out_of_fragment:non_horn`, `compound_goal`, `existential`,
`stratification` и `naf_in_l2` (существующие коды, сохранены), плюс
`defeasible_with_clausal_fragment` (D-FR-4).

Валидация происходит **до** решения; gaps не переинтерпретируются задним числом.

## 6. Где это живёт

Чистая `analyze_routing(theory, query) -> RoutingDecision` в
`engine/inference.py` (там, где уже `select_inference`), вызывается из `verify`.
Ad-hoc отказы в `engine/verify.py` (`out_of_fragment:non_horn`, `compound_goal`,
`stratification`, `naf_in_l2`) и отказы клаусификации становятся следствиями
решения, **сохраняя свои gap-коды**, чтобы существующие наборы тестов остались
зелёными. `engine/explain.py` следует тому же `decision.procedure`, чтобы путь
объяснения не мог разойтись с вердиктом.

Схема и промпт не меняются: фрагмент выводится, а не авторизуется LLM.

## 7. Цикл предложений

Никакой эскалации по gaps. Цикл (Фаза 2) может **заменить структуру** (LLM
предлагает переформулировку, классифицируется `derivable`/`cited`/`hypothesis`/
`rejected`); роутер пересчитывает фрагмент на новой структуре. Это единственный
законный путь смены процедуры внутри прогона, и это аудируемое предложение, а не
догадка движка.

Почему каскад по gaps отвергается, конкретно:

- Для чисто Horn-структуры определённый forward chaining полон по ground-выводу,
  поэтому clausal-процедура не добавляет ничего; для не-Horn содержания требуемый
  фрагмент виден статически до прогона. Значит, повышение по gaps не спасает ни
  одного достижимого случая и рискует сменить семантику.
- `verify` под одной процедурой не может диагностировать «тебе нужна другая
  процедура», не зная конструктов других фрагментов, что нарушает шов
  `docs/logic_layer.md` §2.

## 8. Не-цели

- Поле `fragment`, авторизуемое LLM (второй источник истины, расходящийся со
  структурой).
- Cause-коды вида «тебе нужен L2», возвращаемые `verify` (анализатор знает это
  статически).
- Итеративный каскад с условием остановки.
- Вывод мировой предпосылки из структуры. Она объявляется, всегда.

## 9. Решения

- **D-FR-1 — Набор возможностей, а не авто-процедура.** Флаги объявляют
  допустимые процедуры; они никогда не называют семантику. Семантика остаётся
  объявляемой запросом/харнессом.
- **D-FR-2 — Первый инкремент — A1 (только валидация).** `select_inference`
  сохраняет текущее поведение (`ANKYRA_LOGIC` вкл + цели → clausal);
  `analyze_routing` добавляется как валидатор и точка отказа. Выбор минимально
  достаточной процедуры внутри широкого набора (A2) **отложен** до появления
  продуктового рантайма, где включено несколько возможностей одновременно, и до
  отдельного измерения такого поведения.
- **D-FR-3 — Никакой эскалации по gaps.** Процедура выбирается один раз,
  статически; цикл предложений меняет структуру, а не логику движка.
- **D-FR-4 — Defeasible × дизъюнкция — явный отказ.** Дефолтный слой
  (`engine/defeasible.py`) работает по Horn-замыканию и читает только
  `rule.consequence`, игнорируя `alternatives`. Структура, которая одновременно
  дефолтная и требует clausal-фрагмента, докладывается как
  `out_of_fragment:defeasible_with_clausal_fragment`, никогда не понижается молча.
- **D-FR-5 — Никакого fragment от LLM.** Выводится из структуры.
- **D-FR-6 — Ожидаемый фрагмент объявляет харнесс.** Каждый адаптер коллекции
  ассертит фрагмент своего committed-сэмпла (ProofWriter tier D → `horn`;
  ProntoQA-OOD tier a → `clausal`). Это честный дом для объявления; движок
  выводит.

## 10. План реализации (A1, минимальный диф)

1. `engine/inference.py` — добавить `FragmentFeature`, `RoutingDecision`,
   `analyze_routing(theory, query)`; читать возможности через `get_setting`.
   Оставить `select_inference` без изменений (D-FR-2).
2. `engine/verify.py` — вызывать `analyze_routing` первой; выразить существующие
   отказы (`non_horn`, `compound_goal`, `stratification`, `naf_in_l2`) как исходы
   решения с неизменными gap-кодами; добавить
   `out_of_fragment:defeasible_with_clausal_fragment` (D-FR-4).
3. `engine/explain.py` — заменить ветку `logic_enabled()` на `decision.procedure`,
   чтобы объяснение и вердикт совпадали.
4. Тесты — committed, LLM-free синтетическая коллекция
   (`evals/build_routing_synthetic.py`, `evals/routing_synthetic.py`,
   `evals/data/routing_synthetic.jsonl`), покрывающая каждую фичу фрагмента и
   каждый код отказа; гейтится `tests/test_evals_routing_synthetic.py`. Полный
   `uv run pytest`.
5. Документация — эта заметка; ссылка из `docs/reasoning_roadmap.md` §6 и
   `docs/logic_layer.md` §10.

## 11. План тестирования

- **Юнит (анализатор).** По фиче: Horn-теория → `horn`; дизъюнктивная голова /
  составная цель → `clausal`; constraint / отрицательный литерал → `negation`;
  экзистенциал → `clausal`.
- **Отказ.** Требуемый фрагмент вне набора возможностей → `out_of_fragment` с
  именованным кодом; закрытомирный NAF под clausal → `naf_in_l2`; defeasible ×
  дизъюнкция → `defeasible_with_disjunction`.
- **Инвариант гейта (D-FR-6).** Каждый харнесс коллекции ассертит ожидаемый
  фрагмент; 0 случаев, где структура с дизъюнкцией/экзистенциалом решена
  Horn-процедурой.
- **Регрессия.** Существующие synthetic-наборы L1/L2/defeasible и
  `test_engine_inference.py` остаются зелёными под A1.

## 12. Статус

**A1 реализован.** `analyze_routing` + `RoutingDecision` в `engine/inference.py`;
`verify` смотрит на решение перед диспетчеризацией (существующие отказы сохраняют
свои gap-коды, плюс `defeasible_with_clausal_fragment`); `explain` следует
`decision.procedure`. LLM-free гейт `evals.routing_synthetic` зелёный (**12/12**;
покрыты все фичи фрагмента и все коды отказа). Отложенный инкремент A2 (минимально
достаточная процедура внутри широкого набора возможностей) отслеживается здесь и
является предпосылкой того, чтобы многопроцедурный продуктовый рантайм мог
заявлять больше, чем пиннутый гейт.
