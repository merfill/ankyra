# Немонотонные (defeasible) рассуждения — проектная заметка

Как обрабатывать исключения и дефолты (немонотонное рассуждение) в монотонном
Horn-движке Ankyra. Канонический документ: `docs/defeasible_reasoning.md`.

## 1. Проблема

Движок монотонный: факты и правила только накапливаются, выведенный атом никогда не
отзывается. Но правила из текста бывают двух видов:

- **строгие (strict)** — «все люди смертны», «седан — это автомобиль»: определения,
  без исключений;
- **дефолтные (defeasible)** — «птицы летают»: дефолт, допускающий исключения
  («пингвины не летают»).

На монотонном движке дефолт и исключение срабатывают оба и дают противоречие. Пример
(L3 из `evals/problems.jsonl`):

```
Birds can fly. Penguins are birds, but penguins cannot fly. Tweety is a penguin.
```

Теория: `is_a(?x,bird) => fly(?x)` и `is_a(?x,penguin) => ¬fly(?x)`.
Замыкание выводит и `fly(tweety)`, и `¬fly(tweety)` → `refuted` / `not_proven`.
Честный отказ звуков, но бесполезен.

## 2. Почему «отрицание важнее» — неверно

Наивный приоритет «отрицание побеждает утверждение» ломается на обратном случае:

```
Birds cannot fly. Penguins can fly. Tweety is a penguin.
```

Здесь верный ответ — «да», но приоритет отрицания выбрал бы `¬fly`. Принцип, который
работает **в обе стороны**, — **специфичность / поражение (defeat)**: более конкретное
знание побеждает более общее, независимо от полярности. В обоих примерах правило про
пингвинов конкретнее правила про птиц и потому выигрывает — с любым знаком.

## 3. Стандартные семантики (карта)

| подход | идея | плюс | цена |
|---|---|---|---|
| Negation as failure (CWA) | выводить `C`, если `¬C` не выводимо | direction-agnostic, просто | нужна аккуратная стратификация |
| Default logic (Reiter) | `premise : justification / conclusion`; расширения | точно | несколько расширений, fixed points |
| Answer Set Programming | stable models; `not` в теле | выразительно, «истина» | новый решатель, семантика ASP |
| Well-Founded Semantics (WFS) | единственная трёхзначная модель (true/false/unknown) | всегда определена, единственна | алгоритм alternating fixpoint |
| Defeasible logic (Nute) | strict + defeasible правила, приоритеты | ровно под этот случай | учёт приоритетов/специфичности |
| Argumentation (Dung) | аргументы + атака, grounded/preferred | единообразно решает конфликты | построение аргументов/атак |
| Circumscription / autoepistemic | минимизация аномалий / интроспекция | теоретично | трудно операционализировать |
| Вероятностные | распределение над выводами | градуированная уверенность | иная продуктовая семантика |

**Единой «правильной» семантики нет** — это выбор. Нужно выбрать стандартную, звуковую
и совместимую с текущим движком.

## 4. Отображение на Ankyra

- `Rule.kind` остаётся формой `implication | exception`. **Все правила — дефолты**
  (`Rule.strength` всегда `defeasible`); строги только asserted-факты/аксиомы.
  Ни LLM, ни эвристика по предикату не решают: конфликт `is_a` разрешается
  специфичностью как любой другой, а при невозможности — честно неразрешён. Это
  исключает ложную строгость, когда извлечение выражает свойство через `is_a`
  (например, «Quakers are pacifists»).
- Провенанс уже есть: у каждого выведенного атома `premises` / `used` / `rule_index`, а
  `Hypothesis` фиксирует допущения. Конфликтующие выводы — два дерева; специфичность
  решает, кто кого побеждает.
- Транзитивное `is_a` уже есть и является оракулом специфичности: правило про `C1`
  конкретнее правила про `C2`, когда `is_a(C1, C2)`.
- Статусы ложатся на трёхзначную семантику:
  `true → supported`, `false → refuted`, `unknown → unsupported`.
- Сила ответа: поле `Answer.defeasible`, чтобы пользователь знал, что применён
  дефолт, а не строгий факт.

## 5. Решение (реализовано за `ANKYRA_DEFEASIBLE`)

Принять **defeasible logic как negation-as-failure поверх строгого Horn-ядра, со
специфичностью из `is_a`, под well-founded семантикой**:

1. **Asserted-факты** (и замыкание `is_a` над ними) сохраняют монотонное Horn-замыкание
   (звуково, завершается); все правила — дефолты.
2. **Дефолтное правило** срабатывает, только если его голова не противоречит строгому
   факту или *более специфичному* конкурирующему применению.
3. **Специфичность** сравнивает класс-условия конкурирующих применений через `is_a`;
   строго более конкретное правило побеждает более общее — при любой полярности.
4. **Неразрешённые конфликты** (равная или несравнимая специфичность) честно
   отчитываются как `unsupported` с gap `undecided_conflict:`, без угадывания.
5. Результаты трёхзначные, что совпадает с текущим словарём статусов.

Обоснование: это минимальный стандартный механизм, который решает оба направления,
переиспользует существующую иерархию `is_a` и историю вывода, и не требует нового решателя.

## 6. Алгоритм (`engine/defeasible.py`)

```
effective_closure(theory, assumptions):
    strict = saturate(theory, assumptions, strengths={"strict"})   # + замыкание is_a
    accepted = {}
    repeat:                                                       # ограниченный alternating fixpoint
        base = strict ∪ accepted
        order = транзитивный порядок is_a над base
        candidates = все ground-применения правил (каждое правило — дефолт)
        accepted, unresolved, defeats = resolve(candidates, strict, order)
    until accepted стабильно
    return strict ∪ accepted, unresolved, defeats
```

Разрешение: голова, уже выведенная строго, или чьё отрицание строго выведено, не
добавляется дефолтом (NFA: strict сильнее). Для пары `P` / `¬P` кандидат побеждён,
когда у противоположной стороны есть **строго более специфичное** применение; если
выживает только одна сторона — она принимается, иначе пара *неразрешена* и не
принимается никто.

**Специфичность считается по провенансу двух применений правил**: класс-атомы
(`is_a(subject, class)`) среди прямых посылок тела сравниваются строгим порядком
`is_a`. Кандидаты перечисляются матчингом тел против замыкания (а не чтением одного
сохранённого доказательства), поэтому наличие нескольких выводов не прячет
класс-несущий.

## 7. Провенанс и объяснение

- `refuted` показывает отрицательную ветку; строгое `contradiction` показывает **обе**
  ветки в `Explanation.conflict` (пункт B3, сделано).
- **Разрешённая** победа дефолта прикрепляет `Explanation.conflict`
  (`kind=defeasible`, `status=resolved`, `defeated=attacking`) с отставленным правилом и
  `reason` = свидетелем `is_a` (например, `penguin is-a bird`).
- **Неразрешённый** конфликт показывает оба конкурирующих правила
  (`status=undecided`, `defeated=none`) и `reason`, почему специфичность не сработала
  (например, `no is_a relation decides between quaker and republican`); цель несёт gap
  `undecided_conflict:`.
- LLM-наррация не выбирает: промпту наррации велено следовать трейсу и прямо говорить,
  когда конфликт не удалось разрешить.
- `materialize_rule_morphisms` удалён (пункт B2), поэтому побеждённые и побеждающие
  правила могут попадать в трейс.

## 8. Инварианты и совместимость

- Монотонность (D3) сохраняется для **строгого ядра**; defeasible-слой — отдельное,
  аудируемое *эффективное замыкание* поверх, а не мутация теории.
- Фича за флагом (например `ANKYRA_DEFEASIBLE`, по умолчанию off), поэтому текущее
  поведение остаётся baseline.
- Звуковость не меняется: ни один вывод не выдаётся без дерева; конфликты, не
  разрешённые специфичностью, остаются `unsupported`.

## 10. Открытые вопросы / риски

- **Завершаемость**: fixpoint ограничен (`_MAX_ITERATIONS`), вселенная конечна. Выдача
  статуса `budget` при исчерпании пока не подключена.
- **Нет иерархии**: без `is_a` между конкурирующими классами специфичность
  неопределена → пара остаётся неразрешённой (честное unknown, без угадывания).
- **Специфичность локальна по полярности**: сравниваются классы, только когда
  конкурирующие посылки делят субъект; конфликт через несвязанные предикаты (например,
  `militarist` против `pacifist` без явного отрицания) невидим.
- **Строгих правил нет**: определение в принципе может быть перебито более конкретным
  дефолтом. Строгость принадлежит asserted-фактам; настоящую таксономию можно завести
  фактами, а не выводить правилами.
- **Продуктовая семантика**: это осознанный выбор, а не факт; его нужно зафиксировать и
  пересматривать, если продукту понадобятся градуированные или вероятностные ответы.
