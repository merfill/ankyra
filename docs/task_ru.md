# Техническое задание — Ankyra: гибридный нейро-символический движок рассуждений

> Русская версия для чтения. Каноничный документ — `docs/task.md`.

## 1. Назначение и границы

Ankyra — домен-независимый гибридный нейро-символический движок рассуждений. На
входе — задача на естественном языке, содержащая набор условий и вопрос; на
выходе — пошаговая механически проверяемая трассировка рассуждения и ответ вместе
с логическим статусом этого ответа.

Ключевой принцип: **LLM предлагает, символический движок решает.** LLM не владеет
истиной. Предлагать она может свободно, но каждое предложение детерминированно
классифицируется в одну из категорий:

| категория | условие | действие движка |
|---|---|---|
| `derivable` | уже выводится из текущей теории | принимается только как нарратив |
| `cited` | новый факт, заземлённый дословной цитатой из текста | добавляется в аксиомы |
| `hypothesis` | новое знание, которого в тексте нет | пишется в леджер гипотез с меткой `H` |
| `rejected` | не проходит схему, safety или проверку цитаты | отбрасывается с кодом причины |

В объёме: дедукция до неподвижной точки, унификация с переменными, обнаружение
противоречий, субсумпция через `is_a`, ответ с явным учётом гипотез и объяснение,
построенное механически из истории вывода доказательства.

Вне объёма: поиск по внешнему корпусу или хранилищу фрагментов — Ankyra не
поисковая система и фрагментов у неё нет; вход — одна самодостаточная задача.
Также вне объёма v0: числовое/статистическое скоринг и арифметика сверх
отложенного builtin-слоя (см. Открытые решения, D1).

## 2. Формальная постановка

**Вход.** Задача на естественном языке, содержащая условия (факты, ограничения,
правила «если … то …») и вопрос.

**Выход.**
- Пошаговая трассировка рассуждения.
- Финальный ответ либо честная констатация недоказуемости.
- Статус ответа и, когда применимо, гипотезы, от которых он зависит.

**Типы ответа.**
- `yes_no` — цель `phi` замкнута.
- `open` — цель `phi` содержит переменные `?x`, которые надо связать.
- `instruction` — цели нет (`phi = null`); запрос — это набор условий для проверки.

**Статус.** `supported | insufficient | unsupported | refuted`, плюс процессные
состояния `no_progress | budget`.

**Гарантии.**
- Звуковость гарантируется **относительно формализации и явного леджера гипотез**.
  Ответ `proven` не использует гипотез; ответ, зависящий от гипотез, всегда
  помечается `proven_under(H)`.
- Полнота дедукции гарантируется движком (прямой вывод до неподвижной точки).
  Полнота формализации не заявляется.

## 3. Принципы и инварианты

1. **Никаких фактов, принадлежащих LLM.** Ничто не попадает в теорию без либо
   валидной цитаты (`cited`), либо явной метки гипотезы (`hypothesis`). Легаси-цикл
   «добавить предикаты» отвергается полностью.
2. **Монотонность** (включена сейчас, переключается политикой позже). Теория только
   растёт: добавляются аксиомы, гипотезы пишутся в леджер, цель никогда не
   ослабляется, ни одна посылка не удаляется.
3. **Свобода в предложении, детерминизм в классификации.** LLM может свободно
   именовать предикаты и предлагать правила; классификация предложения всегда
   детерминирована.
4. **Теория и вопрос разделены.** Фаза 0 выдаёт их отдельными артефактами; вопрос
   никогда не утверждается как факт.
5. **Каждый шаг проверяем.** Шаг объяснения соответствует реальному ребру вывода в
   графе вывода либо идентифицированной гипотезе.
6. **Сила ответа явная.** `proven`, `proven_under(H)` или `not_proven`.

## 4. Модель данных

Все модели — Pydantic.

- `Object` — каноническая вершина: `id`.
- `Morphism` — стрелка: `predicate`, `subject`, `object`, `modality`, `quote`,
  `negated`. Отрицание — тот же предикат с `negated = true`; отдельного
  отрицательного имени нет. Модальность — типизированное поле, а не часть имени
  предиката.
- `Rule` — Хорн-клауза: `conditions: list[Morphism]` (AND) → `consequence: Morphism`.
  `kind ∈ {implication, exception}`; `source ∈ {quote, hypothesis:<id>}`.
- `Theory` — `objects`, `morphisms` (утверждённые аксиомы), `rules`.
- `Query` — `conditions` (Gamma), `target` (phi, может содержать `?x`), `variables`,
  `answer_type`.
- `Fact` (внутренний для движка) — замкнутый атом плюс история вывода: `used: frozenset`,
  `witness: str`, `rule_index: int | None`, `axiom: bool`.
- `Hypothesis` — `id`, `kind ∈ {rule, fact}`, `payload`, `wave`, `rationale`.
- `Verdict` — `status`, `bindings`, `gaps`, `matched`, `shelf`.
- `WaveRecord` — `wave`, `proposal`, `category`, `reason`, `verdict_after`.
- `Answer` — `value`, `strength ∈ {proven, proven_under, not_proven}`, `hypotheses_used`.

Модели извлечения структуры (то, что реально сочиняет LLM; сама онтология
собирается детерминированно):

- `Slot` — заполнитель роли: `id` | `set` (AND) | `variants` (OR) | `exclude`.
- `StructAtom` — `predicate` (без модального префикса), `subject: Slot`, `object: Slot`,
  `modality ∈ {permit, obligation, forbidden, neutral}`, `negated`, `quote`.
- `StructRule` — `antecedent: list[StructAtom]`, `consequent: StructAtom`,
  `kind ∈ {implication, exception}`, `quote`.
- `ProblemStructure` — `objects`, `facts`, `rules`, `variants`, `references`.
- `QuestionStructure` — `facts`, `ask` (единственная цель, может быть null), `rules`,
  `variables`.

## 5. Фаза 0 — декомпозиция задачи

### 0.1 Выделение вопроса
Отделяем описательную часть от вопросительной и определяем `answer_type`. Граница
явная; дальше вопрос обрабатывается как самостоятельный артефакт.

### 0.2 Извлечение структуры задачи (LLM, один вызов)
`extract_problem_structure(text) -> ProblemStructure`. LLM выполняет **только**
структурную декомпозицию: объекты, факты, правила («если … то …»), перечисления
(«и»), альтернативы («или»), исключения, модальности, отрицания и цитаты. Готовые
тройки и Хорн-клаузы она **не** пишет; комбинаторика остаётся детерминированному
сборщику. Каждый факт/правило несёт минимальную дословную цитату.

### 0.3 Сборка теории (детерминированно)
- `unroll` — разворачивает `Slot` (наборы/альтернативы/исключения) в морфизмы по
  subject × object; переносит `modality` типизированным полем (в имя предиката она
  НЕ зашивается); опционально понижает модальность до префиксов (`obligation → must_`,
  `forbidden → must_not_`, `permit → may_`) при `ANKYRA_DEONTIC_PREFIXES`; собирает
  `Rule` (`exception` переворачивает `negated` заключения). Без LLM.
- `enrich` — канонизация полярности (`isNot → is_a + negated`), дедуп,
  материализация тривиальных следствий, лечение противоречий и висячих концов. Без LLM.
- `symbolic_check` — проверка, что каждая цитата реально является подстрокой
  источника, имена каноничны, а структура корректна. Без LLM.
- При нескольких сэмплах победитель определяется детерминированным скором:
  покрытие источника цитатами → меньше gaps → компактность (меньше морфизмов/правил).

### 0.4 Извлечение структуры вопроса (LLM, один вызов)
`extract_question_structure(question, theory) -> QuestionStructure`. Онтология
теории встраивается в промпт, чтобы LLM выразила вопрос словами теории. `ask`
(цель) — заключение самого вопроса: переменная `?x` для genuinely открытых
неизвестных («какой/кто/что»), константа иначе, `null` для инструкций. Если вопрос
невыразим словарём теории, он сохраняется дословно, чтобы верификация честно
сообщила `target_unmatched`.

### 0.5 Сборка запроса (детерминированно)
`unroll_query` — `facts → conditions` (Gamma), `ask → target` (phi); затем `settle` —
привязка термов к id теории, снятие эха цели, нормализация полярности и удаление
неиспользуемых посылок (с перепроверкой после каждого удаления). Без LLM.

## 6. Фаза 1 — детерминированное ядро (спина)

- `saturate(theory ∪ Gamma)` — полу-наивный прямой вывод до неподвижной точки на
  конечном универсуме, завершается при отсутствии прогресса. Каждый выведенный факт
  несёт историю вывода (`used`, `witness`, `rule_index`).
- `unify` / `match_goal` — унификация с переменными; `match_goal` возвращает все
  попадания цели с подстановками и историей вывода.
- `complementary` — обнаружение `P` и `¬P` на одной тройке.
- `is_a` — транзитивное замыкание положительных рёбер `is_a`.
- `verify(theory ∪ Gamma ⊢ phi)`:
  - любая комплементарная пара → `refuted`;
  - цель сопоставлена и все посылки использованы → `supported`;
  - цель сопоставлена, но часть посылок не использована → `insufficient`;
  - ничего не сопоставлено → `unsupported`.
  Структурированные пробелы кодируются: `target_unmatched:`, `condition_unmatched:`,
  `unused_premise:`, `contradiction:`.
- **Builtins:** в v0 их нет. Предикаты сравнения — явное отложенное расширение
  (см. D1); интерфейс выставляет единственную точку `evaluate(builtin_atom, subst)`.

Этот слой звуков и полон относительно формализации и никогда не добавляет знание.

## 7. Фаза 2 — направляемый цикл рассуждения

Внутренняя петля детерминирована. Внешняя волна чередует подсказку, свободное
предложение LLM и детерминированную классификацию.

**Шаги волны.**
1. `verify(state)` → вердикт + структурированные gaps.
2. Проверка терминальности: стоп при `supported` / `refuted` / `no_progress` / бюджет.
3. Сборка подсказки для LLM: структура задачи, словарь теории (допустимые предикаты
   и объекты), сводка достигнутого фронта, gaps, цель, допустимые действия
   предложения и правила заземления.
4. Свободное рассуждение LLM → нарратив **плюс одно типизированное предложение**:
   - `reformalize_query` — выразить Gamma/phi словарём теории;
   - `propose_rule` — новое правило (cited или помеченная гипотеза);
   - `assert_cited_fact` — новая аксиома, подкреплённая валидной цитатой;
   - `select_subgoal` — выбрать следующую цель для движка.
5. Детерминированная классификация и валидация предложения: схема,
   safety/range-restriction, проверка цитаты; присвоение
   `derivable | cited | hypothesis | rejected` и применение либо отбрасывание.
6. Запись `WaveRecord`; повторный запуск внутренней петли.

**Леджер гипотез.** Каждая `hypothesis` хранится с id, видом, полезной нагрузкой,
волной и обоснованием. Ответ сообщает, какие гипотезы были использованы.

**Условия остановки.** `supported`, `refuted`, `no_progress` (предложение
идентично предыдущему), исчерпан бюджет (`max_waves`) или нет достижимой гипотезы
(честный `fragment_gap`/`unsupported`).

**Рампа свободы (политика).** Волна 0 может быть разрешающей (свободное именование,
гипотезы разрешены и помечаются); последующие волны могут ограничивать словарь и,
опционально, запрещать гипотезы (`ANKYRA_ALLOW_HYPOTHESES=false`).

## 8. Фаза 3 — объяснение

Трассировка рассуждения строится **механически** из истории вывода: от выигрышной
привязки цели идём по `used`-фактам и рёбрам `rule_index` доказательства и получаем
упорядоченный список шагов, каждый из которых называет правило, подстановки и
цитату или гипотезу, его лицензирующую. LLM может только перефразировать готовый
вывод; вводить факты она не может.

## 9. Оркестрация (LangGraph)

Единый `StateGraph` над Pydantic/TypedDict-состоянием с редукторами для
append-only `history` и `hypotheses`.

Узлы: `identify_question` → `extract_problem_structure` → `build_theory` →
`extract_question_structure` → `build_query` → `verify` →
(`propose` → `classify` → `verify`)* → `explain`.

Поля состояния: `problem_text`, `theory`, `query`, `hypotheses`, `closed_facts`,
`verdict`, `wave`, `max_waves`, `history`, `status`, `answer`.

Условные переходы: после `verify` — в `explain`, если терминально, иначе в
`propose`; после `classify` — обратно в `verify`. Функции маршрутизации чистые;
статус фиксирует узел, а не мутация внутри ребра.

## 10. Конфигурация

Dynaconf, префикс `ANKYRA` (см. `src/ankyra/config/settings.py`).

Есть: `ANKYRA_API_URL`, `ANKYRA_API_KEY`, `ANKYRA_MODEL`, `ANKYRA_TEMPERATURE`,
`ANKYRA_MAX_TOKENS`, `ANKYRA_MAX_TOKENS_EXTRACT`, `ANKYRA_EXTRA_BODY`,
`ANKYRA_REASONING_EFFORT`.

Новые: `ANKYRA_MAX_WAVES`, `ANKYRA_ALLOW_HYPOTHESES` (по умолчанию `true`),
`ANKYRA_STRICT_VOCAB`, `ANKYRA_DEONTIC_PREFIXES`, `ANKYRA_EXTRACT_SAMPLES`,
`ANKYRA_BUILTINS` (по умолчанию `false`), `ANKYRA_LIVE`.

## 11. Примеры (приёмочные тесты)

### Пример A — дождь (чистая дедукция, 1 волна, без гипотез)
- Фаза 0: теория = `{raining()}` с правилом `R1: raining() => isWet(ground)`;
  вопрос `phi = isWet(ground)`, тип `yes_no`, `Gamma = {}`.
- Волна 0 (только детерминированно): `saturate` срабатывает по `R1`; `verify` →
  `supported`.
- Ожидание: «да», объяснение из истории вывода, LLM в цикле не вызывается.

### Пример B — транспорт (абдукция, N волн, гипотезы)
- Фаза 0: теория = факты `hasEngine(X)`, `wheelCount(X,4)`, `power(X,150)`,
  `doorCount(X,4)`; **правил нет** — правила классов в тексте отсутствуют.
  Вопрос `phi = is_a(X, ?c)`, тип `open`.
- Волна 0: замыкание ничего не даёт для `phi`; `verify` → `target_unmatched: is_a`.
- LLM предлагает правила классов и иерархию классов; цитат из текста у них нет,
  поэтому категория — `hypothesis` (`H1`, `H2`, `H3`, `Hh`).
- Повторное замыкание: `is_a(X, motorVehicle)`, `is_a(X, car)`, `is_a(X, sedan)`,
  плюс транзитивное `is_a`. `match_goal(is_a(X, ?c))` связывает `?c`; «самый
  специфичный» теперь **определён** цепочкой `is_a`, а не угадан.
- Ожидание: «X — седан, **при** H1, H2, H3, Hh». С запретом гипотез — честное
  «по тексту не выводится». Этот пример заодно показывает ключевой факт: правила
  классов никогда не были в исходном тексте.

## 12. Критерии приёмки

- Пример A даёт `proven` ровно за одну волну, без гипотез.
- Пример B даёт `proven_under(H)` и перечисляет гипотезы; при
  `ANKYRA_ALLOW_HYPOTHESES=false` — честное недоказательство.
- Ни один ответ не помечается `proven`, если использовалась гипотеза.
- Каждый шаг объяснения отображается на ребро вывода или id гипотезы.
- При temperature 0 и фиксированной модели теория и замыкание детерминированы;
  классификация предложения детерминирована для любого предложения.

## 13. Открытые решения

Ведутся в `docs/implementation_plan.md`; кратко здесь.

- **D1 (сравнения/builtins) — решено.** В v0 их нет; пороги — помеченные
  гипотезы. В v0.1 добавляется минимальный range-restricted builtin-вычислитель
  (`=`, `neq`, `<`, `lte`, `>`, `gte`) за флагом; вариант B (только гипотезы)
  остаётся fallback.
- **Режим гипотез (решено).** По умолчанию разрешающий-с-метками
  (`ANKYRA_ALLOW_HYPOTHESES=true`); строго-только-цитата доступен переключателем.
  В силу ответа идут только те гипотезы, что реально вошли в доказательство.
- **Оркестрация (решено).** LangGraph `StateGraph`, линейный граф с ограниченным
  циклом рассуждения (раздел 9). `langgraph` остаётся зависимостью.
- **Деонтическая модальность (решено).** Модальность — первоклассное поле
  `Morphism.modality`; имена предикатов по умолчанию без префикса. Понижение до
  `must_`/`must_not_`/`may_` в стиле OntoLegal доступно за `ANKYRA_DEONTIC_PREFIXES`
  (с polarity fold и фиксом двойного префикса). Вариант A — всегда префикс —
  остаётся fallback.
